Delivery · 5 min read

Build the ROI model before the proof of concept

It's tempting to start with a prototype — it feels like progress, and stakeholders like seeing something. But if you build first and calculate value later, you'll often find the case was weak from the start, after the budget is already spent.

A four-question filter

Before approving a prototype, we ask clients to answer four questions in writing:

  • What decision or action does this system change? If the output doesn't change what a person or process does next, there's no value to capture.
  • What is that change worth, per unit, per month? Even a rough number is enough to compare against build and run cost.
  • What does it cost to run this at the volume we actually need? Pilots are cheap; production inference, data pipelines, and monitoring are not.
  • Who loses if this doesn't ship? If no one is accountable for the outcome, the project has no natural champion once it gets hard.

Why this filters out most "AI ideas"

Roughly half the use cases we're asked to evaluate don't survive this exercise — not because AI can't do them, but because the value, once quantified, doesn't clear the cost of building and maintaining the system. That's a good outcome: it's much cheaper to learn this on paper than after three months of engineering.

What survives is worth building properly

The use cases that do clear this bar get a real business case attached to them from day one, which makes every later conversation — about scope, timeline, or budget — much easier to have.
